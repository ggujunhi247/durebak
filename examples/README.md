# 협업 예제

[review-loop.example.json](review-loop.example.json)은 두레박의 작업·검토·수정·검증 흐름을 설명하는 **설계 예제**다. 실행기나 확정된 설정 스키마는 아직 없으며, 이 JSON을 실행 가능한 제품 설정으로 안내하지 않는다.

## 시나리오

샘플 프로젝트에서 `limit=0`일 때 기본값이 적용되는 결함을 수정한다. 완료 기준은 0 보존, 누락 시 기본값 적용, 음수 거부다. 이 샘플 프로젝트와 검증 명령은 구현 단계에서 별도 fixture로 만든다.

1. OpenCode 작업자가 0 보존을 구현하고 결과 revision을 제출한다.
2. Claude Code 검토자가 음수 처리 누락을 발견하고 해당 revision에 수정 요청을 연결한다.
3. OpenCode의 같은 세션이 맥락을 이어서 수정하고 새 revision을 제출한다.
4. Claude Code가 새 revision을 검토한다.
5. Codex가 같은 새 revision의 동작을 검증하고 근거를 제출한다.
6. 기준을 충족하면 run을 완료하고 배움 후보를 남긴다.

위 서술은 예상 흐름이다. 실제 시험은 응답 문구를 강제하기보다 결함 발견, revision 변화, 검증 대상 일치, 완료 기준을 확인한다. 역할과 Provider의 대응은 교체 가능해야 한다.

## 함께 확인할 실패 흐름

- 작업자가 offline이면 요청은 만료 시점까지 보관되고 완료로 표시되지 않는다.
- 응답 전에 연결이 끊어지면 같은 코드를 조용히 다시 실행하지 않는다.
- 이전 revision의 검증 성공으로 새 revision을 통과시키지 않는다.
- 동일한 미해결 상태가 반복되거나 한도를 넘으면 needs_attention으로 전환한다.
- 사용자 cancel 이후 새 라운드를 시작하지 않는다.

실제 계약과 기본값은 [구현 현황](../docs/IMPLEMENTATION.md)을 따른다.

## v0.3.0 스펙을 반영한 복구 정책

예제의 runtime_policy는 원자적 claim, 단일 실행 소유권, replay 이벤트의 실행 금지, 무단 backend/세션 전환 방지, 제한된 rate limit 재시도, checkpoint의 정책 digest를 설명한다. outcome은 산출물과 기준별 근거, 미확인 사용량, 실제 정지 상태를 연결한다.

history를 다시 읽어도 새 작업이 시작되지 않아야 하고, 완료 기준이 바뀌면 과거의 통과 근거만으로 완료하지 않아야 한다. 취소 후 실제 실행이 남아 있으면 그 사실을 표시한다. 이 파일은 계속 실행 불가능한 설계 예제다.

## v0.4.0 설계 예제: 효율과 기록

context_policy는 턴 전체의 자동 전달과 원문 확장 예산을 합산한다. cache_policy는 로컬 파생 자료의 재사용과 최종 검증 생략을 구분한다. records_policy는 구조화된 상태에서 모델 호출 없이 문서를 만들고 원본 근거를 보존한다.

예를 들어 검토 세션에는 전체 대화 대신 현재 기준·변경 파일·revision과 관련 finding을 전달한다. 필요하면 정확한 revision의 코드와 로그 일부를 조회한다. 수정 후에는 바뀐 내용만 전달하되, context base가 사라졌으면 짧은 작업 요약부터 복구한다.

[기록 문서 템플릿](records/README.md)은 예상 출력 형식을 설명하며 실제 실행 결과가 아니다.
